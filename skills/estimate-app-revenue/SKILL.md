# App 月收入估算

用可复核证据给出区间，不用下载量、评分或价格凭空反推收入。默认同时分析目标 App 和同一开发者的 App Store 产品组合。

## 输入与默认值

- 必填：一个 App Store App ID；也接受开发者 ID，并先识别 ID 类型。
- 可选：`scope=app|studio|both`、目标月份、storefront、报告币种。
- App ID 默认 `scope=both`，开发者 ID 默认 `scope=studio`；时间为最近一个完整自然月，storefront 为美国，USD 为主口径并附 CNY 换算。
- 若用户指定月份、国家或平台，严格按其范围，不把其他期间或地区的数据混入结论。

## 工作流程

### 1. 建立官方身份与产品组合

先运行：

```bash
python3 scripts/apple_lookup.py APP_ID --country us
```

用输出确认目标 App、`artistId`、开发者名称、平台类型及作品列表。再打开 Apple 官方 App 页面和开发者页面核对。Apple Lookup 结果只证明元数据和产品组合，不证明下载量、内购收入或利润。

若美国 storefront 查不到，先从用户提供的 URL 推断国家，再尝试原始 storefront；仍查不到时报告“该地区不可用或 ID 无效”，不要直接认定产品已下架。

若输入是 App ID，默认沿 `artistId` 展开 Studio；若输入是开发者 ID，记录产品组合后选择下载或收入最集中的 App 深挖。分别统计 iOS/iPadOS 与 `mac-software`，不要遗漏 Mac，也不要把缺少第三方覆盖的产品当作零收入。

### 2. 确认商业化方式

逐个检查头部 App 的 App Store 页面、内购项目和开发者网站，记录：

- 免费、付费下载、消耗型内购、订阅、买断。
- 当前 storefront 可见的价格与周期；价格只能证明商业化能力，不能证明成交量。
- 广告、Web 订阅、企业授权或其他商店收入是否存在。不可观测时标记“未计入”，不得写成零。

### 3. 收集同月定量证据

按 [来源与口径](references/source-scopes.md) 的优先级搜索。至少尝试：

1. 开发者公开数据、财务披露或可验证的一方分析数据。
2. 能给出 App 或 Publisher 月下载量/月收入区间的第三方平台。
3. 第二个独立来源，用于校准第一来源的数量级。

每条证据都记录：页面 URL、抓取日期、指标月份、国家/全球范围、平台范围、币种、gross/proceeds 口径及原始区间。付费墙、登录墙或抓取失败必须如实写明；搜索摘要只可作为线索，不可单独支撑核心数字。

### 4. 对齐范围再计算

只合并“同月份、同地域、同平台、同收入定义、同币种”的数字。必要时使用：

```bash
python3 scripts/calculate_ranges.py --input evidence.json
```

- 同一组合内互不重叠的 App 区间使用 `sum`。
- 同一对象的独立估算只有在口径一致时才可使用 `intersection`；无交集说明来源冲突，不能强行平均。
- `<$5k` 应表示为下界 0、上界 5000、上界不包含；不得取 `$2.5k` 当估算值。
- 汇率必须引用目标月份或分析日的来源与日期；原始 USD 结果仍应保留。
- Apple 抽成、税费和 Small Business Program 等规则应实时核对。开发者到账只能作为假设区间，利润因成本未知通常不能估算。

### 5. 建立头部与长尾结论

先判断收入是否集中在少数 App。下载量只能帮助识别应深挖的头部产品，不得直接乘以自造转化率或 ARPU。Studio 总额优先使用 Publisher 级收入证据；若只能得到 App 级数据，逐项说明覆盖率，并把 Mac、广告、Web 等未覆盖收入列为区间外风险。

当来源给出不同窗口，例如“最近 30 天”和“上个自然月”，不要伪装成完全同月。可用相邻窗口做数量级校验，但必须降低证据等级并说明时间错位。

### 6. 给出证据等级

- **A**：目标月份、目标范围的一方公开数据或可验证后台数据，定义清楚。
- **B**：两个独立定量来源在同口径下大体一致，且 Apple 商业化信息可核对。
- **C**：一个定量收入来源，加官方产品/价格及下载或排名证据支持数量级。
- **D**：只有下载、排名、评论、价格等间接信号；只能给明确假设的情景区间，不得称为可靠估算。
- **证据不足**：没有可验证的收入数字，且建立数值区间会主要依赖自造转化率或 ARPU。此时明确拒绝伪精确估算。

### 7. 输出报告

按 [报告模板](references/report-format.md) 输出。结论必须先写，并至少包含：

- 目标月份与范围。
- App Store 消费者支出 gross 区间。
- 开发者税前到账 proceeds 区间及抽成/税费假设。
- Studio 与目标 App 各自结论；无法拆分时明确说明。
- 3 至 8 条最关键证据链接、观察日期和口径。
- 收入集中度、未覆盖收入、来源冲突和证据等级。

## 硬性约束

- 不把累计下载、累计用户或累计评论当作当月付费用户。
- 不把“免费”当作无收入，不把“有内购”当作已有可观收入。
- 不混用 gross、开发者到账和利润；标题和数字旁都标注口径。
- 不把第三方估算描述成 Apple 官方数据。
- 不用单一来源的小于号区间取中点，不输出无依据的个位数精度。
- 数字证据过弱时扩大区间或输出“证据不足”，而不是补造假设。
- 所有会变化的页面和规则都实时查询；报告注明分析日期。
