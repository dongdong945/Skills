# Git 提交流程

## 概述

用于检查当前改动、生成符合约定的中文 commit message，并完成 `git commit`。

本地提交全权委派给固定使用 `gpt-6-luna`、`max` 的 `git-committer`：由它检查变更、隔离提交范围、暂存、生成信息、提交并确认结果。消息格式以本 Skill 为唯一来源。

## 委派与职责

- 主 Agent 仅交接仓库绝对路径、预期分支与基线提交、允许提交的路径或片段、变更目的、适用约定、实际验证结果和未验证项；由 `git-committer` 自行核对现场并完成整个提交流程。主 Agent 不预先暂存、代写提交信息或代为执行提交。
- 本 Skill 明确授权上述提交委派；实际提交仍须有用户对当前任务的提交授权，不扩展为 push、合并或发布授权。
- 确认专用 Agent 已暴露后按角色调用，模型和推理强度由其配置固定，不替换为其他角色或模型。未加载、不可用或当前会话禁止委派时，说明限制，继续可完成的工作；暂停提交，不由主 Agent 代办或声称已经调用。
- 从交接开始到子 Agent 返回，主 Agent 及其他 Agent 不并发修改同一仓库的 Git 状态或待提交文件。输入、分支或基线变化时，重新确认范围和验证证据，不继续使用旧交接。
- 当前角色是 `git-committer` 时，直接执行下述流程，不再次委派。用户只要求生成信息时，采用只读模式，不暂存或提交。

## 检查边界与停止条件

- 集中读取适用约定、工作区与整个暂存区的状态和 diff，检查提交范围、冲突、明显错误、敏感内容及验证证据。已在当前上下文读取且未变化的约定直接复用；仅在相关状态变化、检查失败或出现新疑点时复查对应部分。
- 复用与当前变更、版本和环境匹配的已有验证证据；不重复执行已通过且仍适用的构建、测试或资源检查。摘要不充分时，只核对影响本次提交的证据，不重新执行整套验证。
- 根据实际改动补充必要检查，不把提交任务扩展为完整代码审计、资源验收或签名体系排查。必要验证仍缺失时返回具体缺口；不得以减少耗时为由跳过明确要求或把未验证表述为通过。
- 工具失败时先核对实际状态和错误原因，有依据地修正后重试一次；仍失败则报告具体阻碍，不反复尝试等价检查。Git 权限拒绝按权限流程处理；提交结果不明确时先核实是否已提交，避免重复写入。
- 范围清晰、必要验证充分且最终暂存区核对完成后，立即生成信息并提交，不继续增加无关检查或等待额外确认。

## 子 Agent 执行步骤

1. **集中检查**：核对仓库、分支、HEAD、授权范围、工作区与整个暂存区 diff、冲突及已有验证证据。无改动时停止；与交接基线不一致时先核实变化。未解决冲突只处理归属清楚且明确授权的部分，涉及无关工作或新的产品决策时保留现场并报告。
2. **暂存并生成信息**：仅暂存允许的路径或片段，核对最终提交集合并按实际 diff 生成下述中文三段式信息，写入临时消息文件。同文件混有无关改动或暂存区含无关内容时，采用保留用户工作区及暂存状态的安全隔离方式；无法可靠隔离时报告阻碍。不使用无范围的批量暂存。用户只要求信息时不暂存或提交，直接返回消息。
3. **提交并核对**：使用 `git commit -F <message-file>`，随后集中核对分支、最新 commit、真实提交范围和剩余工作区及暂存状态，返回实际结果。核查后现场发生变化时，仅重查受影响部分并更新消息。身份、签名、hook 或权限失败时保留现场并报告，不绕过保护；主 Agent 不重复执行提交。

不使用 reset、checkout、stash 或改写历史来清理用户改动，不推送、合并或发布。返回实际分支、commit 标识、完整提交信息、提交范围、验证结果及剩余改动；失败时给出具体阻碍。

## 提交规范

### Prefix

根据 diff 的主导意图选择唯一前缀。跨类别时选主导类别，优先级：`feat > fix > refactor > chore > docs`。

| Prefix | 场景 | Emoji |
| --- | --- | --- |
| `feat` | 新功能、新 UI 组件、新文件实现功能 | ✨ |
| `fix` | Bug 修复、崩溃修复、错误处理修正 | 🐛 |
| `refactor` | 代码重构、架构调整，不改变外部行为 | ♻️ |
| `docs` | 仅文档变更 | 📝 |
| `chore` | 构建配置、依赖更新、CI、工具链维护 | 🔧 |

### 标题

标题格式严格为：

```text
<prefix>: <emoji> <中文动词短语>
```

标题必须单行。动词短语必须中文，英文仅限技术标识符、文件名、类名、方法名、框架名、平台名。必须以动词开头，例如：添加/修复/移除/重构/更新/优化/实现/替换/调整/配置/迁移/支持/处理/完善/拆分/合并/封装/简化/提取/补充/降低/前置/兜底。必须具体描述本次变更内容，禁止“更新代码”“修复 bug”“调整逻辑”等模糊表述。

### Body

除非用户明确要求只生成单行提交信息，否则提交信息必须包含标题和三段式 body。

```text
<prefix>: <emoji> <中文动词短语>

<段落一标题>：<说明本次变更的背景、问题或动机。>

<段落二标题>：<说明复现路径、使用路径、影响范围或验证方式。>

<段落三标题>：<说明实现思路、修复思路、处理方式或风险控制。>
```

不同前缀使用以下段落标题：

| Prefix | 段落一 | 段落二 | 段落三 |
| --- | --- | --- | --- |
| `fix` | 问题描述 | 复现路径 | 修复思路 |
| `feat` | 需求背景 | 使用路径 | 实现思路 |
| `refactor` | 调整背景 | 影响范围 | 重构思路 |
| `chore` | 变更原因 | 影响范围 | 处理方式 |
| `docs` | 文档背景 | 阅读范围 | 更新内容 |

每段独立成段，段落之间空一行。内容必须基于 diff、测试结果、日志或用户提供的信息；不确定的信息不要编造，使用“未覆盖”“未复现”“未验证”等明确表述。禁止添加 Markdown 列表、脚注、测试报告长日志或无关说明。

## 快速检查

- 无改动时直接停止，不生成 commit。
- 有未解决冲突时不提交；在已授权范围内可明确解决的继续处理，否则保留现场并说明具体阻塞。
- 无关改动保持原状，不混入本次提交；已有暂存内容也逐项核对归属，无法安全隔离时再询问。禁止使用裸 `git add -A`。
- 提交标题必须是单行，且动词短语必须是中文。
- 提交 body 必须遵循三段式结构，除非用户明确要求只生成单行提交信息。
- 英文只允许出现在技术标识符里。
- 返回实际分支、提交标识与提交信息；仅生成消息时不虚构提交结果，不按分支名自动追加警告。
- prefix、emoji、标题和 body 结构必须遵循本 skill 的提交规范。
- 整个本地提交流程由固定模型的 git-committer 完成；主 Agent 仅交接并接收结果，不代办提交。
