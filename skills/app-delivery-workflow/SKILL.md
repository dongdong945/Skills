# App Delivery Workflow

在现有主工作目录内顺序交付 App 或较大 Feature 的首个可运行切片。由主 Agent 连续完成需求、界面、业务接入和验证；不自动创建 Git worktree，不依赖 UI/业务实现子 Agent。用户的明确执行偏好优先。

遵循项目已有架构、资源和平台工具约定。Git 提交继续按项目的 `git-commit-workflow` 处理；本 Skill 不扩展提交、推送或发布权限。

## 开工边界

修改前确认：

- 项目根目录、当前分支、基线提交、工作区和暂存区状态；识别并保留已有改动。
- 需求、非目标、首条用户路径、页面入口、核心产品规则和外部契约。
- Figma 节点或明确的设计非目标。复用现有已认可界面时，无需为了流程新建 Figma。
- 必要的 loading、content、empty、error、disabled、retry、submitting 状态及其可观察结果。
- 页面输入、回调、业务输入输出、数据归属、路由和返回行为。
- 用户指定的设备、系统、姿态与允许的验证工具；不机械扩大设备矩阵。

未知改动与本任务重叠、存在未解决冲突、核心规则不明或必需工具不可用时，先保存现场并报告具体缺口。不要把缺少工作树或已移除的实现 Agent 当作阻碍。

## 确认需求与实施顺序

有 PRD、页面流程、Figma 说明或外部契约时，使用 `review-product-requirements` 核对可实现性与验收标准。缺失的核心产品规则需明确，常规实现选择由主 Agent 判断。

只记录足够评审的轻量约定：页面入口与返回、状态名、UI 输入和回调、业务输入输出、取消与失败行为。沿用项目 spec/plan，不另造通用契约系统。

按可独立实现、验证和人工 review 的逻辑 task 顺序推进。每个 task 先读相邻实现，再做满足目标的最小改动；不按文件机械拆分，也不在同一任务内混入无关重构。

## 先运行最小切片

新 App 先建立能启动的外壳与导航；现有 App 保留已验证行为。尽早打通第一条用户路径：启动或进入功能、首屏、核心操作、后续导航、返回和最终结果。

需要先验证 UI 时，以明确的 Mock 或内存依赖表达约定状态，再通过同一接口接入真实业务。Mock 不等于系统副作用已隔离：按场景控制通知、闹钟、支付、权限和外发请求。QA 入口保持显式且仅 Debug 生效，正常入口仍使用正式依赖。

有 Figma 还原任务时使用 `figma-implement-design`；SwiftUI 布局和真实资源遵循相应平台 Skill。没有设计稿时沿用现有组件、token 与外观，不生成占位资源。

## 接入业务与数据

遵循项目已有职责边界和 MVVM/Clean 约定，先追踪状态唯一来源、持久化及依赖装配点。不要为流程新增通用基类、无需求的实体或跨 Feature 抽象。

通过轻量接口将 UI 输入与事件接入业务层；在装配入口替换 Mock，避免为真实依赖重写页面。UI 与业务契约确需变化时，同步修改调用方、失败状态和测试。

按实际风险验证旧数据兼容、迁移失败保护、取消与重试、重复操作、异步过期结果和重新进入后的刷新。记录真实错误，不用静默回退掩盖故障。

## 验证与只读验收

选择与改动风险匹配的最小充分验证，不因机械流程重复构建或运行全量测试。至少确认：

- 首条用户路径可进入、操作、导航、返回并产生正确结果。
- 相关成功、空状态、加载、失败和恢复行为可观察。
- 资源引用正确且实际可见；在约定设备/姿态上无控件遮挡或溢出。
- 业务规则和数据边界有适当的聚焦测试或其他真实证据。
- QA 入口或依赖装配改变后，单独验证无 QA 参数的正常入口。

依照项目批准的工具，区分编译、测试、Preview、模拟器交互与真机验证。证据标明源码版本、设备、系统、姿态、执行内容和限制；不把 Mock、编译或历史截图当作本次设备通过。

实施完成后使用 `delivery-acceptance` 进行只读验收。未使用 worktree 时，跨工作树合并项明确记为不适用，核对当前主目录的变更范围与基线即可。验收发现实现问题时退出只读验收，修复后复验相关范围。

## 提交与交接

每个完成的逻辑 task 先自审、修复并完成必要验证，再按项目提交规则只提交本 task 范围。保留无关暂存和工作区内容，不自动 push、合并或发布。

报告实际变更、commit、验证结果、证据位置、未验证边界和必要人工确认项。用户要求暂停时选择可恢复节点，保存未完成状态和下一步，不把尚未验收的功能写成已完成。
