# 交付验收

对 UI 与业务实现已经合并的 App 或 Feature 做只读验收，判断首个可运行切片是否达到交付门槛。只基于需求、轻量共享约定、代码、提交、Preview、构建、测试和运行证据作结论；缺少证据时标记为未验证，不自行补写产品规则。

## 验收边界

- 在 `app-delivery-workflow` 的集成阶段之后使用，优先检查第一条可运行用户路径。
- 不修改实现文件、不替开发者解决冲突；发现问题后输出触发条件、影响和修复方向。
- 不替代 `review-product-requirements` 的开发前需求评审、`review-cn` 的代码评审或 `figma-implement-design` 的实现过程。
- 不评审埋点、事件上报或分析指标。
- 允许把局部视觉精调、文案和已记录的 Figma 偏差留给人工确认，但不能把核心流程、状态错误或缺失证据包装成视觉待办。

## 验收输入

先确认当前上下文是否包含：

- 集成 worktree、分支和基线提交。
- 需求、Figma 节点或明确的 UI 非目标。
- UI/业务轻量共享约定，包括页面入口、状态名、UI 输入、UseCase 输入输出和文件所有权。
- UI 与业务分支的提交、合并结果和当前工作区状态。
- Preview、构建、测试、模拟器/设备交互等验证证据。

输入不完整时继续做可做的静态检查，同时在“未验证”中明确列出缺口，不得直接判定通过。

## 验收流程

### 1. 确认集成边界

先读取项目 `AGENTS.md`、README、架构说明和任务约定，再检查：

- 当前分支、基线提交、集成提交和 worktree 列表。
- UI 与业务分支是否从同一基线开始，是否存在未提交冲突或未合并提交。
- 变更文件是否符合所有权约定，是否混入无关改动、临时文件或用户已有改动。
- 项目配置、资源目录、路由和共享组件是否被多个 worktree 同时修改。

不使用破坏性 Git 操作清理现场，不把工作区干净误认为功能正确。

### 2. 验证首个用户路径

按需求和共享约定逐步检查：

- App 是否可以启动，目标入口是否可达。
- 首个页面、核心操作、下一步导航、返回/关闭和最终结果是否闭合。
- 路由参数、默认状态、返回结果和重新进入后的刷新行为是否一致。
- 是否出现需求之外的网络、数据库、认证、支付或其他生产行为。
- Mock 数据是否能在真实服务未完成时独立演示首个路径。

### 3. 验证 UI 与业务契约

检查 View、ViewModel、UseCase、Repository、DataSource 和依赖注入之间的边界：

- UI 是否使用约定的数据形状或 UseCase 接口，而不是私自创建另一套字段和状态。
- View 是否直接承担网络、数据库、文件访问或复杂业务规则。
- ViewModel 是否能表达 loading、content、empty、error、disabled、submitting、retry、cancel 和 completed 等适用状态。
- Mock 替换真实依赖的位置是否明确，接入真实依赖后是否无需重写页面布局。
- 失败、重复触发、取消、重新进入和异步完成后的状态是否有可观察结果。

### 4. 验证数据和状态一致性

只检查需求范围内适用的规则，重点确认：

- 状态是否有唯一来源，完成、撤销、重试或刷新后相关页面是否能同步。
- 缓存优先、后台刷新、强制刷新、空缓存、分页和失败后的显示是否符合约定。
- 日期 key、日历、时区、用户/账号作用域、首次/再次和当前/历史等边界是否与实现一致。
- 数据库、缓存或资源结构变化是否包含必要的 migration、旧数据兼容和升级失败处理。
- 数据错误、服务失败、本地存储失败和用户取消是否被错误地合并成同一种成功结果。

### 5. 验证 Figma、设备和资源证据

检查已有 Preview 和资源证据，不以截图数量代替视觉结论：

- 参考设备、紧凑设备和宽屏设备是否都已验证；设备名称应稳定且可读。
- Preview 是否按设备/模块/View 组织，例如 `Docs/Preview/<Device>/<Module>/<ViewName>.png`；多状态使用明确状态后缀。
- 参考设备匹配不应通过复制一份设备专用 View 实现；检查安全区域、长文本、图片比例、滚动、控件和内容是否重叠或溢出。
- Figma 资源是否保留来源，是否提供项目要求的 `@2x/@3x`，是否放在模块或子模块的 `Folder with Namespace` 下。
- 不得把生成图片、私自绘制图片、放大裁切图片或占位图当作资源验收通过；缺失资源应单独记录。
- 把已知的局部颜色、间距、字体或文案偏差列为人工 UI 确认项，并与功能问题分开。

### 6. 核对验证证据

按项目 `AGENTS.md` 使用批准的工具，并分别记录：

- 构建是否通过，以及构建目标、配置和日志范围。
- Preview 是否成功，以及渲染了哪些设备、页面和状态。
- 单元测试或接口测试是否存在、执行了哪些范围；不能用 App 构建替代测试结论。
- 模拟器交互、真实设备交互和静态检查分别覆盖了什么。
- 工具不可用、签名失败、目标不存在、运行未完成或只完成静态检查时，明确写成未验证或阻塞。

## 结论规则

按严重程度输出问题，优先列问题再列总结：

- `P0`：核心路径不可运行、数据/状态契约错误、合并冲突未解决或无法确认交付边界。
- `P1`：高概率造成返工、跨页面状态不一致、旧数据失败、资源结构错误或关键验证缺失。
- `P2`：局部视觉偏差、文案、可维护性问题或不影响首个路径的补充项。

使用以下结论之一：

- **阻塞，不能交付**：存在 P0，或关键 P1 使核心路径、数据正确性或验收证据不成立。
- **可交付，需人工确认**：核心路径和关键证据成立，只剩明确隔离的视觉、文案或非关键体验项。
- **未完成验收**：实现可能可用，但缺少必要输入、工具或证据，无法形成可靠结论。

## 输出格式

```text
## 结论
- 状态：阻塞，不能交付 / 可交付，需人工确认 / 未完成验收
- 验收范围：页面、状态、设备、提交和验证工具
- P0：N 个
- P1：N 个
- P2：N 个

## 问题清单
### [P0/P1/P2] 标题
- 位置：文件、页面、状态或流程节点
- 证据：代码、提交、截图、日志或需求约定
- 触发条件：什么情况下发生
- 影响：用户流程、数据、合并、资源或验收风险
- 建议：最小修复方向或需要确认的决策

## 已验证
- 已实际完成并有证据支持的范围

## 未验证
- 缺失的输入、工具、设备、测试或运行证据

## 人工确认项
- 不阻塞首个切片，但需要人工确认的 UI、文案或体验差异

## 交付建议
- 修复顺序、是否可以继续人工确认、下一步验证方式
```

没有发现问题时，明确写“未发现阻塞问题”，同时列出未验证范围和人工确认项。不要只输出“通过”，也不要把未执行的验证写成已完成。

## 停止条件

遇到以下情况先停止验收并报告：

- 集成分支、基线或变更范围无法确认。
- UI 与业务仍存在未解决的同文件冲突或共享约定漂移。
- 核心产品规则、数据契约或导航结果未确认。
- 项目要求的构建、Preview 或测试工具不可用，且没有替代证据。
- 发现需要修改实现或做产品决策才能继续；验收 Skill 不代替这些工作。
