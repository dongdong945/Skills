# 回写 Obsidian 候选知识

把任务产出的可靠经验写入 `/Users/dongdong/Documents/Obsidian Vault/outputs/qa`。只创建候选知识，不直接晋升到 `wiki/`，不自动提交或推送 Vault。

## 写入门槛

仅当以下条件全部满足时写入：

1. 结论能在未来类似任务中改变判断、步骤或验证方式，而非只描述本次完成了什么。
2. 结论已有代码、测试、运行日志、一手资料或用户明确确认支持。
3. 适用对象、范围和失效条件可以说明清楚。
4. 搜索 `wiki/` 与 `outputs/` 后，结论尚未被有效知识完整覆盖，或同一候选确有新的验证证据需要补充。

任一条件不满足就跳过回写。不要为了证明使用了 Skill 而制造笔记。

## 工作流程

1. 汇总本次任务中经过验证的结论、证据、适用范围、风险和仍未验证事项。
2. 使用标题关键词、项目名、功能名、错误文本和关键技术名词在 Vault 中查重。
3. 若 `wiki/` 已有等价结论且无需修订，停止写入。若新证据会改变已有知识，创建一篇候选并在“关联知识”中指向原笔记，不直接修改 `wiki/`。
4. 若 `outputs/qa/` 已有同一候选，完整读取后更新该文件；保留用户已有内容，只补充新证据、边界和更新时间。
5. 否则在 `outputs/qa/` 创建一篇主题明确的 Markdown。每个任务最多新增或更新一篇候选，相关结论合并表达。
6. 使用系统当前日期填写 `created` 和 `updated`。仅在当前任务 ID、仓库、commit 或来源 URL 确实可得时记录，不要猜测。
7. 写入后重读文件，检查 frontmatter、证据与结论是否一致，并确认没有敏感信息。

## 候选格式

```markdown
---
type: learning
status: candidate
scope: <适用范围>
verified: true
created: YYYY-MM-DD
updated: YYYY-MM-DD
sources:
  - <任务链接、仓库路径、commit、代码位置或原始 URL>
tags:
  - <最多三个检索标签>
---

# <可检索的具体标题>

## 候选结论

<可以直接指导未来行动的结论>

## 适用范围

<适用对象、前置条件和不适用情形>

## 验证证据

<代码位置、commit、测试、日志摘要、一手资料或用户确认>

## 证据边界

<未覆盖内容、时效性事实、失败条件和仍需验证事项>

## 关联知识

<已有 Obsidian 链接；没有时写“暂无”>
```

## 禁止写入

- API Key、访问令牌、密码、个人隐私、受保护业务数据或完整敏感日志。
- “已修改文件”“测试通过”“已提交”等没有复用价值的任务流水账。
- 未复现的错误归因、未经验证的架构设想或把第三方估算包装成事实的内容。
- 已由 `AGENTS.md`、项目文档或现有 wiki 完整覆盖且无需修订的规则。
- 大段复制原始网页、聊天记录或代码；只保留可追溯摘要和来源。

## 输出约束

- 写入时告诉用户笔记的 Vault 相对路径；跳过时只在该判断对用户有价值时简短说明原因。
- 保持 `type: learning`、`verified: true` 和 `status: candidate`，等待整理流程去重、处理冲突和晋升。
- 不修改 `raw/`、`wiki/`、`system/` 或 `.obsidian/`。
