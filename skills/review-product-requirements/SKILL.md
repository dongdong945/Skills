# 产品需求技术评审

把需求评审成“可实现、可验证、可追责”的开发输入。只基于需求、设计、现有代码和仓库规则作判断；缺少证据时标记为待确认，不自行补写产品决策。

## 评审边界

- 评审对象可以是 PRD、Issue、设计说明、流程图、页面清单、接口/数据约定或它们的组合。
- 先确认本次范围、目标平台、版本、用户身份、默认路径和明确的非目标。
- 按需读取 [项目需求评审基线](references/project-baseline.md)，再检查当前项目的 `AGENTS.md`、README、Docs、方案文档和相邻实现；当前项目事实优先于基线。
- 不把代码评审、视觉 1:1 检查或技术方案设计冒充需求完整性结论；可以指出它们所需的缺失输入。
- 本 Skill 不评审埋点、事件上报或分析指标；只有当它们影响核心业务行为时，才指出需求存在外部依赖缺口，不展开事件规则。

## 工作流程

### 1. 建立需求证据表

将需求拆成可核对条目，并为每条记录：来源位置、主体、触发条件、前置条件、动作、结果、状态变化、数据来源、失败处理和验收方式。把“未说明”和“推断”分开。

至少覆盖：

- 目标与范围：用户问题、成功结果、包含项、非目标、版本限制。
- 角色与身份：新用户/老用户、登录状态、订阅状态、权限拒绝、身份切换和数据归属。
- 流程与状态：入口、正常路径、返回/关闭/重试/跳过、加载、空、错误、禁用、处理中、完成和恢复中断。
- 规则与边界：最小/最大值、数量上限、日期和时区、默认值、单选/多选、互斥项、重复提交、幂等性和取消。
- 数据与副作用：来源、字段类型、持久化、缓存、刷新、网络/数据库/API、通知、购买、相机、上传或系统权限。
- 架构与导航：模块归属、View/Presentation、ViewModel、UseCase、Repository、DataSource、路由输入和返回结果。
- 设计与资源：Figma 节点、页面状态、设备尺寸、适配规则、资源来源、`@2x/@3x` 倍率、裁切、命名空间和缺失处理。
- 验收与验证：每条行为如何验收，哪些由静态检查、构建、Preview、单元测试、接口测试或人工交互验证。

### 2. 检查完整性

对每个用户可见入口逐步追问：谁在什么条件下做什么，系统显示什么，数据如何变化，下一步去哪里，失败后如何恢复。特别检查“有页面但没有行为”“有按钮但没有结果”“有结果但没有来源”“有错误文案但没有恢复动作”。

进一步确认：

- 状态是否有唯一来源，完成/撤销/重试后是否能回流到所有受影响页面。
- 缓存优先、后台刷新、强制刷新、分页、空缓存和请求失败后的显示策略是否明确。
- 异步任务是否定义取消、重复触发、in-flight 请求复用、超时和恢复行为。
- 日期是否定义日历、时区、日期 key、跨午夜和夏令时边界；数据是否按用户或账号正确隔离。
- 数据库表、字段、缓存格式或资源结构变化是否需要 migration、兼容旧安装或版本回滚说明。
- 需求是否说明导航参数、返回结果、dismiss/push 后的默认状态和恢复路径。
- 需求是否说明模块独立性、复用边界、命名规则和不应新增的抽象。
- 测试 target、Preview、构建工具或外部依赖是否真实存在，验证方式是否可执行。

把缺失分成三类：

- **阻塞开发**：无法确定状态机、数据契约、权限、核心规则、导航结果或验收结果。
- **高风险缺口**：可以临时实现，但容易造成返工、数据错误、状态不同步、旧安装失败或跨页面不一致。
- **非阻塞缺口**：文案、局部视觉细节或不影响当前纵向切片的补充项，但必须记录负责人和截止点。

### 3. 检查冲突

按以下顺序比对，不要只做关键词搜索：

1. 需求正文与流程图/页面清单/状态说明。
2. 正常路径与关闭、返回、重试、取消、异常和恢复路径。
3. 字段定义与示例、默认值、边界值、接口/数据库/缓存契约。
4. 同一规则在不同页面、用户身份、日期、来源或版本下的表述。
5. 需求与当前项目规则、已有行为、架构边界、资源目录和已确认非目标。

冲突报告必须指出冲突双方、触发条件和影响；不要替产品选择其中一方。若仅是术语不一致，标为“需要统一定义”，不要直接判定为逻辑冲突。

### 4. 检查准确性与可执行性

将模糊词替换成可验证问题：

- “适当”“及时”“正常”“支持多种情况”分别是什么条件和上限？
- “完成后”“返回后”“首次”以哪个事件、持久化状态或页面生命周期为准？
- “可选”“不可用”“隐藏”是 UI 表现、权限结果还是业务规则？
- “失败”包含网络失败、服务拒绝、超时、解析失败、用户取消、资源缺失还是本地存储失败？
- 一个术语、状态、ID、日期 key 或资源名是否在页面、代码、接口、数据库和验收中保持同一含义？
- 需求中的“复用”是复用视觉模式、协议、数据链路还是具体类型？是否会造成模块耦合？

准确性结论分为：`可直接实现`、`存在可解释歧义`、`与现有事实冲突`、`缺少外部契约`。每项结论都要引用证据或明确写“需求未提供”。

### 5. 检查实现准备度

确认需求可以被拆成可人工 review 的 task，并记录：

- 受影响的页面、模块、路由、数据层、资源和工程配置。
- task 之间的前置依赖、共享文件和文件所有权。
- 是否需要先创建测试 target、迁移、资源目录或基础 App Shell。
- 每个 task 的最小验收方式、独立提交边界和合并风险。
- 哪些部分可以先用 Mock，哪些必须等待真实外部契约。

不要因为需求写了很多页面就直接判定可开发；如果数据、状态、资源、迁移或验证依赖没有闭合，应在结论中指出。

### 6. 输出开发结论

默认使用以下结构，问题优先：

```text
## 结论
- 状态：可进入开发 / 补充后进入开发 / 暂不能进入开发
- 阻塞问题：N 个
- 高风险问题：N 个
- 非阻塞待确认：N 个

## 问题清单
### [P0/P1/P2] 标题
- 位置：需求章节、页面、流程节点或字段
- 证据：原文/图示/现有代码事实
- 问题：缺失、冲突或不准确之处
- 触发条件：什么情况下发生
- 影响：开发、测试、数据、用户流程或后续维护风险
- 建议：需要产品确认或补充的最小决策

## 已确认范围
- 可以直接实现的规则和明确非目标

## 影响范围与实现准备度
- 页面、模块、路由、数据、资源、工程配置、迁移和 task 依赖

## 验收缺口
- 每个缺口对应的状态、边界、数据或验证方式

## 待产品确认
- 只列会改变实现或验收结果的问题
```

优先级含义：`P0` 阻塞主流程或会造成严重数据/用户风险；`P1` 高概率返工、状态错乱、旧安装失败或验收争议；`P2` 局部歧义、可维护性或非关键体验问题。没有问题时明确写“未发现阻塞问题”，并列出仍未验证的风险。

## 评审纪律

- 先读完整输入和相关上下文，再下结论；不要只根据标题或一张截图推断全流程。
- 把“需求没有说”与“实现不支持”分开；前者是需求缺口，后者是技术约束或现有行为冲突。
- 不因“看起来合理”替用户决定产品规则；需要选择时给出选项、影响和待确认项。
- 不把构建通过、截图存在或代码已有实现当成需求正确的证明；必须逐条对照规则、状态、边界和验收。
- 代码事实只能用于验证现状、发现冲突和确定影响，不应反向替需求补写未确认的产品规则。
- 结论应足够让产品补需求、开发拆 task、测试编写用例；避免只写“需要更清晰”。
