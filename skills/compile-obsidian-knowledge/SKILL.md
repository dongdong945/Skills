# 整理 Obsidian 知识

维护 `/Users/dongdong/Documents/Obsidian Vault` 中从 `outputs/` 到 `wiki/` 的晋升链路。遵守 `system/Knowledge-Boundaries.md` 和 `system/Daily-Loop.md`，不自动提交或推送 Vault。

## 开始前

1. 读取 `system/Home.md`、`system/Knowledge-Boundaries.md` 和 `system/Daily-Loop.md`。
2. 检查 Vault Git 状态和目标文件 diff。保留用户现有改动；目标笔记存在含义不明的未提交修改时跳过该笔记并说明原因。
3. 使用 `rg` 查找 `outputs/` 下 `status: candidate` 的 Markdown。本轮最多处理 10 篇，更多内容拆成后续可人工 review 的批次。
4. 同时搜索 `wiki/` 与其他候选，建立重复、关联和冲突关系。
5. 没有候选时报告“本轮无待整理候选”并停止，不创建空报告或修改索引。

## 晋升门槛

候选必须同时满足以下条件才能进入 `wiki/`：

- frontmatter 明确包含 `status: candidate` 和 `verified: true`。
- 结论已经在真实任务中使用或验证至少一次，而非只完成资料摘录。
- 证据可追溯到代码、commit、测试、运行结果、一手资料或用户确认。
- 适用范围、不适用情况和时效性边界明确。
- 与当前代码、官方资料和现有 wiki 没有未解决冲突。
- 内容未来仍有复用价值，且不是可随时从源码确认的短期细节。

不满足门槛时保留 `status: candidate`，补充可确认的缺口或在结果中列出下一步；不要为了完成整理而降低标准。

## 整理动作

### 晋升新知识

1. 根据内容选择现有 `wiki/` 子目录；没有匹配目录时才创建范围清晰的新目录。
2. 提炼结论和执行方法，不大段复制候选正文。保留来源、适用范围、证据边界、验证状态和相关 Obsidian 链接。
3. 使用当前日期填写 `created` 和 `updated`，并采用与相邻 wiki 笔记一致的 frontmatter。
4. 将原候选更新为 `status: promoted`，添加 `promoted_to: "[[目标笔记]]"` 和 `updated`；保留原始证据作为审计链。

### 合并重复知识

1. 选择范围更完整、证据更强的现有笔记作为主笔记。
2. 只补充主笔记尚未覆盖的新结论、来源和边界，不机械拼接全文。
3. 将被合并候选更新为 `status: merged`、`merged_into: "[[主笔记]]"` 和当前 `updated` 日期。

### 处理冲突和过时内容

- 当前代码和运行证据优先，其次是一手资料，再其次是现有 `wiki/`、候选和 `raw/`。
- 无法消解的冲突不得晋升；保留双方来源，并列出需要补充的验证。
- 易变化事实必须重新核对。无法核对时标记可能过时，不静默覆盖旧结论。
- 旧 wiki 已失效且证据充分时，在原笔记中明确更新或弃用状态，保留变更原因和替代链接。

## 更新索引

- 新增或重命名 wiki 笔记后，更新 `system/Home.md` 的知识入口。
- 优先补充现有索引，不创建重复索引页。
- 检查孤立 wiki 笔记、失效链接和没有来源的稳定结论，并在结果中列出。

## Skill 候选

若同一流程已经在多个真实任务中重复出现，步骤稳定、输入输出明确且边界可验证，将其列为 Skill 候选。只提出候选名称、触发条件和证据，不在本流程中创建或修改 Skill。

## 输出约束

- 汇总本轮晋升、合并、保留、冲突和过时项，并列出修改过的 Vault 相对路径。
- 明确未处理的剩余候选数量和下一批范围。
- 不修改 `raw/` 中的原始材料，不删除候选，不自动执行 Git commit 或 push。
